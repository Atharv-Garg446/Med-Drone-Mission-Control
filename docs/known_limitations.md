# Known Limitations, Scope Boundaries & Future Engineering Roadmap

This project is an **educational software and simulation prototype** demonstrating autonomous UAV mission planning, dynamic airspace/disaster reasoning, and ArduPilot SITL closed-loop integration. It is **not** certified, flight-tested on physical hardware, or approved for real-world BVLOS medical operations.

---

## 1. Current Technical Limitations

| Domain | What Is Implemented & Verified | Honest Limitation / What Is Not Claimed |
| :--- | :--- | :--- |
| **DigitalSky Airspace Validation** | Implements the exact OpenAPI 3.0.0 contract (`POST /flightplan/validate/airspace`, `X-API-VERSION: 1`, `source`, `x-auth`, `x-correlation-id`, base64 GeoJSON `geom`, `maxAltitude <= 400 ft`) verified against `digitalsky_interactive_maps_api_v1.0.yml`. | Live execution against `digitalsky.dgca.gov.in` requires an authenticated DGCA pilot JWT token (`x-auth`). Without credentials, the system reports `UNAUTHORISED_NO_PILOT_TOKEN` and `official_clearance = False`. Local Jaipur scenario zones are labeled `SYNTHETIC_FIXTURE`. |
| **Mappls Airspace Layers** | Documented and classified in `MapplsAirspaceLayerSpec` (`MAP_VISUALIZATION_ONLY`). | Mappls Airspace Web SDK (`mappls.airspaceLayer`) is a JavaScript vector-tile visualization widget and does not expose a REST API for raw polygon export or autonomous route clearance. |
| **GDACS Live Disaster Feed** | Live HTTP ingestion from `https://www.gdacs.org/gdacsapi/api/Events/geteventlist/SEARCH` and `/api/polygons/getgeometry`, episode deduplication, expiry filtering, disk caching, and mandatory attribution (`"Global Disaster Awareness and Coordination System, GDACS."`). | GDACS provides macro-scale disaster centroids, bounding boxes, and alert polygons (`FL`, `EQ`, `TC`). It does **not** provide street-level flood depth, building collapse geometry, or micro-scale landing pad clearance, and is not an aviation authority. |
| **Simulated Sensor & Obstacle Avoidance** | ArduPilot SITL C++ raycaster (`AP_Proximity_SITL`, `PRX1_TYPE = 10`) casts 8 horizontal rays in C++ against world obstacles in `AC_PolyFence_loader`, populates `AP_OADatabase`, emits `DISTANCE_SENSOR` and `ADSB_VEHICLE` (`OA_DB`) over MAVLink, and triggers `AP_OABendyRuler` (`OA_TYPE = 1`) horizontal avoidance in `AUTO` mode. | 1) `AP_Proximity_SITL` is a 2D horizontal 8-sector raycaster (`0°, 45°, ..., 315°`), not a full 3D point-cloud LiDAR or Gazebo optical camera renderer.<br>2) Because `AP_Proximity_SITL::get_distance_to_fence` uses binary search on `[0, 200 m]` (`first probe = 100 m`), world obstacle cylinders must have a ray chord crossing the `100 m` midpoint probe to be bisected by `PRX1_TYPE = 10`. |
| **Medical Delivery & Custody Confirmation** | Site-suitability-aware selection between `hover` (`15 m AGL` descend + `MAV_CMD_DO_GRIPPER` release + climb) and `land` (`MAV_CMD_NAV_LAND` + ground `MAV_CMD_DO_GRIPPER` + `MAV_CMD_NAV_DELAY` 5 s dwell + `MAV_CMD_NAV_TAKEOFF` retakeoff), backed by ArduPilot's `SIM_Gripper_Servo` (`SERVO9`). | Release is confirmed via causal simulated actuator feedback (`STATUSTEXT: Gripper Released`) and ground dwell completion (`release_provenance = "simulated_ground_gripper_release_after_dwell"` or `"simulated_hover_gripper_release"`), with `recipient_handover_verified = False` (no physical load-cell or human cryptographic signature). |
| **Energy & Vehicle Model** | Grounded in `MedDrone-Hexa-16` (`5.5 kg` empty, `3.2 kg` 6S 16 Ah battery, `284.16 Wh` usable energy at `20%` reserve floor, `8.0 kg` max payload, `17.5 kg` MTOW) and coupled to SITL via `flightstack/params/med_drone_hexa_16.json` (`--model hexa:med_drone_hexa_16.json`, `num_motors = 6`, `disc_area = 1.4255 m²`, `maxVoltage = 25.2 V`, `refVoltage = 22.2 V`, `battCapacityAh = 16.0`) and `sitl_delivery.parm` (`FRAME_CLASS = 2`, `SIM_BATT_VOLTAGE = 25.04`, `SIM_BATT_CAP_AH = 16`). | 1) In Python (`flightstack/vehicle_model.py`), aerodynamic power uses momentum theory + Glauert forward-flight induced power and steps down cargo mass after each stop (`3.5 kg -> 1.5 kg -> 0.0 kg`).<br>2) In ArduPilot C++ (`SIM_Gripper_Servo.cpp`), the simulated servo gripper attaches a single `1.0 kg` external load on takeoff (`11.2 + 1.0 = 12.2 kg` gross takeoff mass) and drops `1.0 kg` on the first release rather than modeling two independent `2.0 kg` + `1.5 kg` cargo bays, and `SIM_Motor.cpp` scales motor current linearly with thrust without Glauert translational lift reduction. |
| **Weather Subsystem** | Intentionally deferred per project scope decision. | No live meteorological / wind-field subsystem is integrated in this sprint so engineering effort remained focused on 4D NFZs, SITL obstacle avoidance, and delivery state-machine correctness. |
| **Single-UAV vs. Multi-UAV Control** | Primary SITL flight stack controls **one** autonomous UAV (`JAIPUR_SINGLE_UAV`, `fleet_size = 1`). | Simultaneous multi-UAV SITL control and tactical airborne deconfliction between multiple drones are out of scope for the current sprint (`simulate_fleet.py` and `vrp_scratch.py` remain a kinematic logistics simulator). |
